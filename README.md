# ANYQ

Операционная система для торговли в Казахстане: касса, склад, закупки, кабинет
владельца и B2B-витрина заказов — одним приложением, которое ставится на обычный
телефон или планшет и работает без интернета.

Не для ресторанов. Ресторанный код в репозитории есть, он остался от прежней
версии и помечен как legacy; продукт делается для магазинов, складов, небольших
сетей и дистрибуции.

## На чём всё держится

Три решения, из которых следует почти всё остальное в коде:

**Журнал — это правда, остаток — кэш.** `StockMovement` только дописывается,
`Stock.quantity` пересчитывается из него. Любая цифра остатка обязана сходиться с
суммой своих движений, и это проверяется — тестами, командой резервного
копирования и утренней сводкой владельцу. Продукт, который не может доказать свои
числа, для учёта бесполезен.

**Пересчёт не закрывает магазин.** Инвентаризация применяет разницу, которую
насчитал человек, а сервер отматывает журнал к моменту пересчёта. Поэтому считать
можно при работающей кассе, а не ночью.

**Касса работает без сети неделю.** Продажи копятся в очереди и уходят сами.
Отсюда токен на тридцать дней, идемпотентность на всём, что двигает деньги и
товар, и отказ от многого, что требует постоянного соединения.

## Запуск на своей машине

```bash
docker compose -f docker-compose.dev.yml up -d   # Postgres на 5433
npm install
npm run db:migrate
npm run dev:api                                   # http://localhost:4000
npm run dev:pos                                   # касса
npm run dev:admin                                 # админка платформы
npm run dev:orders                                # витрина заказов и сайт
```

Если 4000 занят: `PORT=4010 npm run dev:api`, а в `apps/pos/.env` и
`apps/admin/.env` — `VITE_API_URL=http://localhost:4010`.

## Проверки

```bash
npm test          # 1152 модульных, секунды, ничего не нужно поднимать
npm run test:db   # 479 интеграционных, нужен Postgres, около пяти минут
npm run onboard:check   # весь путь заведения магазина против живого сервера
npm run backup:verify   # копия снимается, разворачивается и сверяется
npm run uptime:check    # отвечают ли боевые службы прямо сейчас
npm run uptime:test-alert  # работает ли сам канал уведомлений
```

Оба прогона идут сами на каждый толчок в `main` и на каждый pull request
(`.github/workflows/tests.yml`): типы во всех четырёх приложениях, модульные,
интеграционные против своей чистой базы и сборка. До 15.09.2026 их не запускал
никто, кроме человека, который их писал.

Отдельно, раз в пятнадцать минут, проверяется, что боевые службы отвечают
(`.github/workflows/uptime.yml`). Запускается это у GitHub, а не на Railway, и в
этом весь смысл: планировщик живёт рядом со службами и потому не может
сообщить, что они лежат.

В адресе базы пишите `127.0.0.1`, а не `localhost`. Docker Desktop под Windows
публикует порт дважды — `com.docker.backend` слушает IPv4, `wslrelay` слушает
IPv6, — а имя `localhost` разрешается в оба адреса, и Node выбирает между ними
гонкой. Когда она разрешается не в ту сторону, соединение не открывается:
прогон краснеет с «Can't reach database server» вразнобой, в разных файлах, и
воспроизводится через раз. Проверено руками: в одну и ту же минуту `localhost`
отказывал, а `127.0.0.1` и `[::1]` подключались оба. Литеральный адрес гонку
убирает — один адрес, один ретранслятор.

Postgres для тестов поднимается `docker compose -f docker-compose.dev.yml up -d`.
После запуска контейнера дождитесь не `pg_isready`, а настоящего запроса: пока
база доигрывает журнал, порт уже открыт и `pg_isready` отвечает «готова», а
отказ приходит на первом запросе. Прогон это переживает
(`apps/api/src/db-startup.ts`), но своё ожидание лучше строить так:

```bash
until docker exec anyq-db psql -U anyq -d anyq_test -tAc "select 1" >/dev/null 2>&1; do sleep 2; done
```

Запущен он без `fsync` намеренно: прогон очищает все таблицы перед каждым тестом,
а ожидание записи на диск под Docker Desktop стоит секунд. База одноразовая —
`anyq_test` вытирается каждым прогоном, `anyq_dev` поднимается миграциями и
сидом за минуту.

`onboard:check` намеренно отказывается работать против базы, где уже есть
компании: он создаёт компанию, а удалить её нельзя — маршрутов удаления нет, и
это не упущение.

## Документы

Начинать отсюда:

- [LAUNCH_CHECKLIST](docs/LAUNCH_CHECKLIST.md) — что перед первым платящим
  клиентом сделано и доказано, а что ждёт человека.
- [PRODUCT_PLAN](docs/PRODUCT_PLAN.md) — что построено и, честно, что нет.
- [PILOT_READINESS_AUDIT](docs/PILOT_READINESS_AUDIT.md) — сверка обещаний с
  кодом, включая единственное, что сейчас держит коммерческий запуск.

Эксплуатация:

- [PRODUCTION_RUNBOOK](docs/PRODUCTION_RUNBOOK.md) — развёртывание, проверка
  после него, тариф, обслуживание.
- [BACKUP_RUNBOOK](docs/BACKUP_RUNBOOK.md) — копии, восстановление, переезд на
  другой сервер.
- [PILOT_PLAYBOOK](docs/PILOT_PLAYBOOK.md) — день запуска у клиента.

Бизнес:

- [PILOT_CHARTER](docs/PILOT_CHARTER.md), [PRODUCT_VISION](docs/PRODUCT_VISION.md).

Цены, себестоимость, маркетинг и план до первых денег в этом репозитории не
лежат и лежать не будут: репозиторий открытый, а это цифры, по которым читается
заработок с магазина и то, на чём можно уступить. Они у владельца отдельно.

## Цвет

Два токена, которые нельзя разлучать: `--accent-fill` — заливка, `--on-accent` —
то, что на ней пишут. Заливка зелёным с `color: #fff` даёт 2.35 в тёмной теме
(норма 4.5) и 4.41 в светлой: подпись на главной кнопке продукта формально
нечитаема, а касса стоит у окна. Порознь эти два значения разъезжаются по темам,
вместе — нет.

`--accent` остаётся зелёным, **которым пишут**: цена, активная вкладка, значок.
Для заливок он не годится ни в одной теме.

Проверяется это не на глаз. Обход страницы считает контраст каждой видимой
строки против того, что за ней на самом деле, и его стоит прогнать после любой
правки палитры — так нашлись и обе эти ошибки, и то, что плитка отсутствующего
товара красится служебным цветом браузера для `disabled`.

## Как здесь принято писать

Комментарий объясняет, почему так, а не что делает строка. Если решение спорное —
в комментарии стоит альтернатива и причина, по которой её не выбрали. Тест,
который не падает, когда ломают то, что он охраняет, считается отсутствующим:
проверять это принято ломанием, а не верой.
