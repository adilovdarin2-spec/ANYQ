# ANYQ: запуск пилота в production

Проект готов к пилоту после выполнения всех пунктов ниже. Они проверяемые:
«сервер запустился» не равен готовности учёта.

## Перед первым деплоем

1. Создать отдельную PostgreSQL-базу в регионе, соответствующем политике
   хранения персональных данных клиента, и задать `DATABASE_URL`.
2. Задать `NODE_ENV=production`, `JWT_SECRET`, `VAPID_PUBLIC_KEY`,
   `VAPID_PRIVATE_KEY`, `ALLOWED_ORIGINS`. API намеренно не стартует в production
   без них и в сообщении говорит, зачем нужно именно это значение.

   Пару VAPID сгенерировать: `npx web-push generate-vapid-keys`. До 2026-09-09
   этот пункт был неправдой: ключи откатывались на пару, лежащую в этом
   репозитории, и сервер спокойно стартовал. Приватный ключ, который может
   прочитать любой, — это не слабый ключ, а его отсутствие: подписать
   уведомление «новый заказ» в браузер владельцу мог кто угодно.

   `ALLOWED_ORIGINS` — домены фронтендов через запятую. Без него в production
   был бы откат на localhost, и все три приложения получали бы отказ CORS,
   причём в логе сервера не было бы ничего: ошибка видна только в консоли
   браузера. Теперь сервер не стартует и говорит, что задать.

   `VAPID_SUBJECT` не секрет (адрес для жалоб push-сервиса) и имеет разумное
   значение по умолчанию.
1б. Включить второй фактор у платформенного аккаунта. Это единственная учётная
   запись, которая видит все компании, и до включения её защищает один пароль.

   ```
   API_URL=https://api... ADMIN_EMAIL=... ADMIN_PASSWORD=... node scripts/mfa-qr.mjs
   ```

   Скрипт делает первый шаг и кладёт рядом страницу с QR-кодом. **Второй шаг —
   код с телефона — за человека не делается никем**, и это не формальность:
   сервер держит секрет «в ожидании», где тот ничего не делает, и включает его
   только после кода, доказавшего, что секрет дошёл до телефона. Ввести код за
   владельца — значит подтвердить то, чего проверка и должна не допускать: что
   ключ никуда не дошёл, а второй фактор уже включён.

   Пока код не введён, вход работает по-старому — запереть себя невозможно.
   После включения **сохранить коды восстановления**: они показываются один раз
   и хранятся хешированными, второго шанса нет. На странице с QR лежит ключ от
   учётной записи, которая видит все компании, — отсканировали, удалите файл.

2а. Задать `MAINTENANCE_SECRET` — общий секрет для служебных эндпоинтов. Без
   него они отвечают 404, и планировщик из пункта «Эксплуатация» будет
   выглядеть работающим и не делать ничего.
3. Настроить HTTPS, домены admin/POS/заказов и CORS только на эти домены.
3а. Задать переменные сборки фронтендов. Их читает Vite **в момент сборки** и
   впекает в бандл; переменная окружения на работающем сервере на них уже не
   влияет:

   | Переменная | Кто читает | Что будет, если не задать |
   |---|---|---|
   | `VITE_API_URL` | все три | бандл уходит на `http://localhost:4000` — браузер клиента стучится в собственную машину |
   | `VITE_ORDERS_URL` | касса, админка | ссылка на витрину не показывается |
   | `VITE_POS_URL` | сайт заказов | кнопка «Войти в кассу» не показывается |

   Собирать только через `npm run build:deploy` — он собирает три приложения и
   затем читает получившиеся файлы, отказываясь отдать бандл с `localhost`
   внутри. Railway собирает этой же командой, так что мимо неё не пройти.

   Отдельно: **`.env.local` в каталоге приложения побеждает переменную
   окружения.** Файл, забытый после отладки, тихо перенаправит боевую кассу на
   чужой адрес — именно так бандл в этом репозитории какое-то время указывал на
   `localhost:4010`. Проверка это ловит.
4. Выполнить `npm run migrate:deploy --workspace=packages/db` до запуска новой
   версии. В текущей версии обязательны миграции `20260905110000_link_sales_to_shifts`
   и `20260905120000_add_sale_returns`.
5. Создать платформенный аккаунт — единственное, чем можно войти в админку:

   ```
   ADMIN_EMAIL=you@company.kz ADMIN_PASSWORD='...' npm run admin:create --workspace=packages/db
   ```

   Пароль не короче 12 символов, и команда откажется принять те, что встречались
   в этом репозитории или в каждом словаре. Повторный запуск с тем же адресом
   ничего не ломает: он скажет, что аккаунт уже есть, и ничего не изменит
   (`--reset-password`, если нужно сменить пароль). Аккаунт видит и меняет все
   компании на платформе — включите ему второй фактор в панели до того, как в
   базе появятся данные клиента.

   **`npm run seed` на продакшене запускать нельзя.** Он создаёт демонстрационные
   компании — кафе, аптеку, выдуманные продажи. До 2026-09-09 он был
   единственным, что создавало админа, поэтому на боевой базе его приходилось
   запускать вместе с демо-данными; теперь он на production отказывается
   работать вовсе.

## Проверка после деплоя

0. Прогнать проверку подключения — она проходит весь путь, которым подключают
   клиента, на сервере, который только что настроили:

   ```
   API=https://api... ADMIN_EMAIL=... ADMIN_PASSWORD=... npm run onboard:check
   ```

   Платформенный аккаунт → компания → точка → тариф → сотрудник с PIN → вход
   кассы → товар → стартовый остаток → смена → продажа → сводка владельца →
   сходимость остатка с журналом → номера документов → PIN владельцу, его вход и
   ссылка на кабинет → отказ менеджеру в кабинете → список программ для переезда
   и разбор чужого файла. Двадцать девять шагов; интеграционные тесты проверяют
   код, а это проверяет **этот** сервер: докатились ли миграции, задан ли
   `JWT_SECRET`, та ли это база, и не падает ли что-нибудь на компании, которой
   четыре минуты от рождения, — состояния, которого нет ни в одном тесте, потому
   что все они начинают с готовой фикстуры.

   Три шага добавлены 2026-09-10 и закрывают дыру, из-за которой проверка
   молчала о самом главном. Компания создаётся с владельцем **без PIN-кода** —
   то есть до отдельного действия владелец не может войти никуда. Каждое
   настоящее подключение это действие делает, а проверка — нет, и потому ни разу
   не проверила ни вход владельца, ни его кабинет. Номер документа присваивает
   триггер базы: сервер с недокатанной миграцией выдаёт документы без номера, и
   узнаёт об этом бухгалтер клиента. А разбор чужого файла — то, с чего
   начинается разговор с магазином; если он не работает на этом сервере, знать
   об этом надо до встречи.

   Проверка создаёт компанию и **удалить её не может**: маршрутов удаления нет
   намеренно, компанию с документами удалять нельзя. Поэтому она отказывается
   работать, если компании уже есть. Запускать до создания настоящего клиента —
   или на отдельной базе. Созданная компания называется «ПРОВЕРКА ПОДКЛЮЧЕНИЯ —
   удалить перед запуском», чтобы её нельзя было принять за чужую.

0а. Прогнать smoke по свежей базе — до того, как в ней появится хоть один
   настоящий чек:

   ```
   API=https://api... npm run smoke
   ```

   Он проводит магазин через рабочий день (продажа, повтор той же продажи,
   возврат, приёмка, перемещение с недостачей, размещение, пересчёт полки,
   списание, заказ и частичная поставка) и заканчивает сверкой остатка с
   журналом движений. Юнит-тесты этого не ловят по определению: они не могут
   упасть на недокатанной миграции или на `DATABASE_URL`, смотрящем не туда.

   Он **пишет настоящие данные и за собой не убирает**. На новой базе это и
   нужно; на базе работающего магазина запускать нельзя.

   Код выхода `0` только если всё прошло. Если он пишет «checks passed, but N
   could not be run» — задайте `DATABASE_URL`, иначе проверка отзыва доступа не
   выполняется вовсе.

   Пункты 1–5 ниже — то же самое руками, для случая, когда smoke упал и надо
   понять, где именно.

1. Создать тестовую компанию: магазин + склад, владелец, кассир и два SKU,
   один из которых с партиями.
2. Открыть смену, провести наличную, Kaspi и карточную продажи; проверить, что
   каждый чек виден в серверной сверке смены.
3. Выполнить частичный возврат годного товара и брака. Первый должен вернуть
   остаток, второй — оставить след без прироста доступного остатка. Повторный
   возврат не должен превысить количество исходного чека.
4. Провести чек офлайн, восстановить сеть и убедиться, что смена и чек
   появились по одному разу. Закрыть смену и сверить пересчитанную кассу.
5. Создать B2B-заказ, проверить резерв, выдачу и отмену: доступный остаток не
   должен уходить ниже нуля.

## Эксплуатация

0. Поднять планировщик. Он не опция: очередь фискальных чеков сама себя не
   разбирает, таблица ключей идемпотентности растёт, пока её не чистят, а
   утренняя сводка владельцу целиком построена на том, что кто-то дёргает
   эндпоинт — без планировщика она не уйдёт никогда.

   **На боевом сервере поднят 2026-09-10** — служба `maintenance` в проекте
   ANYQ, из того же репозитория, ветка `main`. Создана так:

   ```
   railway add --service maintenance --repo <owner>/<repo> --branch main      --variables "API_URL=https://api...."      --variables "MAINTENANCE_SECRET=<тот же, что у api>"
   ```

   `RAILWAY_SERVICE_NAME` Railway подставляет сам по имени службы, задавать его
   не нужно. Проверка, что планировщик живой, — не логи, а метрики API: в
   `GET /metrics` должны появиться `POST /maintenance/*`. Пятнадцать минут без
   них означают, что служба не запущена, и выглядит это ровно как исправно
   работающий сервер.

   ```
   API_URL=https://api... MAINTENANCE_SECRET=... npm run maintenance
   ```

   Один проход и выход — так его вызывает cron или Railway Cron. Постоянный
   процесс — `npm run maintenance:loop` (интервал в
   `MAINTENANCE_INTERVAL_SECONDS`, по умолчанию 60 секунд); на Railway это
   отдельный сервис с `RAILWAY_SERVICE_NAME=maintenance`. Отдельный процесс, а
   не цикл внутри API: цикл в веб-процессе конкурирует с кассирами за event
   loop, а чек, опоздавший на минуту, не стоит ничего.

   Коды выхода: `0` — проход прошёл, `1` — что-то не удалось, `2` —
   `MAINTENANCE_SECRET` не задан. Первая же строка лога говорит, разбирается
   очередь или ОФД на этом сервере не настроен вовсе.

1. Делать ежедневный backup БД; раз в месяц восстановить его в отдельную базу
   и записать фактические RPO/RTO.
2. Подключить алерты на недоступность API, ошибки 5xx, ошибку миграции,
   заполнение БД, неотправленные чеки пилотных касс и ненулевой код выхода
   планировщика.

   Цифры, в которых написан устав пилота, отдаёт сам сервер:

   ```
   curl -H "x-maintenance-secret: $MAINTENANCE_SECRET" https://api.../metrics
   ```

   Доля успешных ответов и p95 по времени — общие и по каждому маршруту, плюс
   список маршрутов, которые в цель не укладываются. Отказы (4xx) считаются
   отдельно от ошибок (5xx): кассир, которому отказали в продаже в долг, — это
   не сбой сервера, и мешать их в одну цифру значит не увидеть ни того, ни
   другого. Счётчики живут в памяти процесса и обнуляются при рестарте, так
   что это картина «с последнего деплоя», а не история; для истории — снимать
   их тем же расписанием, что и остальное.
3. Запретить прямое изменение `stocks` и `documents`: остатки меняются только
   документами и `stock_movements`.
4. До приёма фискальных платежей подключить выбранного казахстанского ОФД/ККМ
   через его официальный API, провести тестовый контур и подтвердить схему у
   бухгалтера клиента. Провайдера и доступы выбирает владелец бизнеса.
