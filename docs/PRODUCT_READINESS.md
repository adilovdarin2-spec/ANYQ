# ANYQ — контракт готовности продукта

> **Scope — 2026-09-05.** This contract applies to retail, warehouses,
> distribution and stores. Restaurant workflows are out of scope: not sold, not
> positioned, not developed further, and not enabled for new companies. The
> code that exists stays where it is — deleting a working module nobody is
> offered costs more than it returns — but nothing in this contract, the price
> list or the public site may promise it. Until 2026-09-09 this header sat
> above a table that listed «Ресторан» as a mandatory contour and a roadmap
> that planned split bills; both are gone.

Этот документ превращает идею «система для любого бизнеса» в проверяемый
продуктовый контракт. Он дополняет `PRODUCT_VISION.md`: там — направление,
здесь — что должно быть истинно в данных, интерфейсе и эксплуатации до
масштабирования на десятки клиентов.

## Неподвижные принципы

1. **Одна запись о реальном действии.** Продажа, приёмка, перемещение,
   списание, возврат и пересчёт — неизменяемые документы с автором, временем,
   причиной и ссылкой на первичный документ. Остаток — производная/кэш, а не
   единственный источник истины.
2. **Работа не должна зависеть от сети.** У кассы и кладовщика есть локальная
   очередь команд. Повтор отправки одной команды никогда не создаёт вторую
   продажу или второе списание.
3. **Меньше данных и прав.** Пользователь видит только свою компанию, роль
   открывает только нужные действия; PIN не является общим паролем смены.
4. **Режимы не смешиваются.** Базовый магазин не видит аптеку или сложный
   склад. Пакет добавляет данные и маршруты, а не отдельную копию продукта.
5. **Каждое число объяснимо.** В карточке товара и отчёте можно пройти от
   текущего остатка и прибыли к документам, строкам и действиям пользователей.

## Единая модель данных

| Сущность | Инвариант | Минимальные поля и связи |
|---|---|---|
| Компания | Строгая граница арендатора | страна, часовой пояс, валюта, тариф, пакеты, юрданные, статус |
| Локация | Магазин, склад и производство — разные места | тип, адрес, GLN (опционально), рабочие часы, фискальная конфигурация |
| Пользователь/роль | Роль проверяется сервером на каждом чувствительном действии | сотрудник, роль, статус, PIN-хэш, последний вход |
| Товар | Один товар имеет одну базовую единицу и явные коэффициенты упаковок | SKU, GTIN/штрихкод, название на ru/kk, НДС, единица, весовой флаг, цена, min/max, срок хранения |
| Партия/серийный код | Партия не объединяется с другой партией | товар, номер партии, срок, закупочная цена, поставщик, Data Matrix/серийность |
| Ячейка | Адрес нормализован и принадлежит локации | зона, ряд, стеллаж, уровень, ячейка, capacity, статус блокировки |
| Документ | Черновик можно менять; проведённый нельзя | тип, номер, статус, автор, дата бизнеса, ссылки, строки, вложения |
| Движение | Только append-only; отмена — обратным движением | товар, локация, ячейка/партия, delta, причина, документ, автор, timestamp |
| Команда синхронизации | Один clientCommandId применим ровно один раз | компания, устройство, ключ, payload hash, результат, время обработки |

Никакой запрос по `id` не может обходить `companyId`; это требование относится и
к файлам, печати, webhooks и экспортам.

## Карта жизненного цикла товара

```text
каталог → заказ поставщику → приёмка/партия → размещение в ячейку
       → резерв → продажа/отгрузка/производство → возврат или списание
       → инвентаризация/корректировка → архив и аудит
```

Для каждого перехода обязательны: права, валидация доступного остатка, атомарная
транзакция, движение журнала, событие аудита, понятный экран ошибки и безопасный
офлайн-повтор. Отрицательный остаток запрещён по умолчанию; его разрешение —
отдельная политика владельца и всё равно оставляет предупреждение в аудите.

## Обязательные сценарии

| Контур | Должен уметь пользователь | Критерий принятия |
|---|---|---|
| Касса | сканировать, искать, взвешивать, скидка по праву, наличные/карта/смешанная оплата, возврат | два одинаковых офлайн-повтора создают один документ; смена сходится с деньгами |
| Приёмка | принять частично, расхождение, партия/срок, фото накладной, разместить | нельзя принять больше документа без явной причины; остаток и себестоимость обновлены атомарно |
| Склад | адресное хранение, перемещение, пересчёт, блокировка ячейки, трансфер между локациями | движение из ячейки нельзя провести при недостатке; исходная и целевая стороны трансфера сверяются |
| Заказы | резерв, сборка, частичная отгрузка, отмена/возврат, долг клиента | резерв отделён от физического остатка; просроченный резерв имеет владельца и правило снятия |
| Производство | рецепт, выпуск партии, списание сырья, себестоимость выпущенного | ингредиенты списываются по всем ячейкам и партиям; отмена выпуска оставляет объяснимый обратный след |
| Аптека | Data Matrix, FEFO, партии, срок, карантин, возврат поставщику | уникальный код не продаётся дважды; при недоступной внешней маркировке продажа попадает в контролируемую очередь |
| Владелец | выручка, маржа, касса, дефицит, срок годности, аномалии, экспорт | каждая карточка KPI раскрывает исходные документы и фильтры |

## Казахстан: выпуск без юридических иллюзий

- Платформа **не хранит PAN/данные банковских карт**: терминал или платёжный
  провайдер принимает карту, ANYQ хранит только безопасную ссылку/статус
  платежа. Это резко уменьшает область PCI DSS, но не отменяет оценку
  интеграции и договорных требований.
- В боевом Казахстане фискальная продажа имеет состояние `ожидает ОФД →
  фискализирована | ошибка`. Обычная печать POS не может называться
  «фискальным чеком» до ответа зарегистрированной ККМ/ОФД. Нужны номер ККМ,
  данные ОФД, URL/QR фискального чека, retry и сверка неподтверждённых чеков.
- Персональные данные граждан РК хранятся в базе на территории Казахстана.
  До выбора провайдера оформляются реестр данных, сроки хранения, DPA,
  процедура удаления/выгрузки и журнал доступа.
- Для аптек Data Matrix — не «ещё один штрихкод»: это поштучный жизненный цикл
  с очередью обмена с оператором маркировки, ответами, повторами и запретом
  молча продать код, который уже выбыл или не найден.
- Язык интерфейса: русский и казахский, сумма в тенге, даты/чеки в часовом
  поясе локации. Налоговые ставки и правила — конфигурируемые, не зашитые в UI.

## Надёжность и безопасность: baseline до первого платного клиента

| Риск | Контроль |
|---|---|
| Повтор команды после обрыва сети | `Idempotency-Key` / `clientCommandId`, unique индекс, сохранённый ответ первой обработки |
| Две кассы продают последний товар | транзакция с блокировкой/условным уменьшением остатка, серверный ответ «нет в наличии» |
| Утраченный телефон | привязанное устройство, отзыв сессии, ротация refresh-token, PIN rate-limit, удалённый logout |
| Ошибка сотрудника | обратный документ с причиной и правом, а не правка истории |
| Взлом API | object-level tenant checks, rate limits, schema validation, журнал admin-действий, секреты вне репозитория |
| Потеря базы | ежедневный backup, проверяемое восстановление, RPO/RTO, мониторинг очередей и ошибок |
| Ошибка релиза | миграции с rollback-планом, staging на копии схемы, feature flags, canary-пилот |

## Эксплуатационный дизайн

**Первый запуск — это мастер из 7 шагов:** компания → формат → локация →
фискальность → команда → 30–100 SKU → тестовая смена. Импорт всегда даёт
предпросмотр, карту колонок, отчёт ошибок и возможность отменить до проведения.

**Необходимые состояния экрана:** нет сети, синхронизация N из M, конфликт,
нет прав, пустой каталог, товар не найден, камера/сканер недоступен, печать не
настроена, закрытая смена, истёкшая партия. Нельзя оставлять пользователя с
техническим кодом ошибки.

**Дизайн кассы:** крупные touch-цели, контрастная сумма, одно главное действие,
подтверждение только у необратимых операций, функциональность без мыши,
адаптация под 10" планшет и desktop, ru/kk, доступность клавиатуры. Скорость
первой продажи важнее плотности отчёта.

## Метрики и пороги решения

| Метрика | Цель пилота | Действие при отклонении |
|---|---:|---|
| Первая успешная продажа | < 30 минут после обучения | упростить мастер/каталог, назначить владельца запуска |
| Успешная синхронизация команд | ≥ 99.9% | разбирать все dead-letter команды ежедневно |
| Сверка остатка top-SKU | ≥ 98% | цикл пересчёта, найти причину по движениям |
| Продажи без помощи спустя 7 дней | ≥ 90% смен | улучшить конкретный сценарий, не обучать «в обход системы» |
| Время ответа критичного API | p95 < 500 мс онлайн | трассировка, лимиты, индексы, деградационный режим |
| Поддержка | все P1 < 1 часа до реакции | ротация, шаблоны, статусная страница |

## Очерёдность реализации

### P0 — нельзя продавать без этого

1. Единая идемпотентная очередь всех изменяющих остаток/деньги команд.
2. Атомарные резервы и списания с конкурентным доступом; тесты на гонки.
3. ККМ/ОФД адаптер с очередью и сверкой; платёжный терминал без хранения карт.
4. Полный audit trail, экспорт и восстановление резервной копии.
5. Тенант-изоляция, MFA владельца, отзыв устройств, rate limits и мониторинг.

### P1 — пакет для реальной операционной точки

1. Массовый импорт с качеством данных, номенклатура упаковок и GTIN.
2. Резервы/сборка/частичные поставки, покупки и кредитный контроль.
3. Полный lifecycle партий, FEFO, просрочка/карантин/возврат.
4. Офлайн-склад: приёмка, пересчёт, перемещение с разрешением конфликтов.
5. Приборная панель исключений вместо пассивных «красивых графиков».

### P2 — вертикали и рост

1. Интеграция маркировки лекарств и режим БАД с 1 сентября 2026 /
   прослеживаемостью с 1 марта 2027.
2. Стандартизированные logistics labels: SSCC/GLN для дистрибуции.
3. Сеть: несколько точек под одним владельцем, сводка по сети, перемещения
   между магазинами как обычная операция, а не исключение.
4. API/интеграции бухгалтерии, банков, marketplace; webhook retries и
   мониторинг партнёров.

## Definition of Done для любой новой функции

Функция не считается готовой, пока не имеет: пользовательского сценария и
состояний ошибок; server-side прав; tenant filtering; схемы/валидации; аудита;
идемпотентности если она меняет деньги или остатки; локализации; аналитики;
unit и интеграционных тестов; метрики/алерта; миграции и rollback-плана;
инструкции поддержки. Для фискальности, персональных данных и маркировки нужна
отдельная юридическая/партнёрская приёмка — код сам по себе её не заменяет.
