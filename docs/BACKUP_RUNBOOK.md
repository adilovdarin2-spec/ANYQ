# Резервные копии и восстановление

Хартия пилота делает **проверенное восстановление** условием выхода в
коммерческий запуск. Этот документ — сама процедура, а не описание намерения.

Копия, которую никогда не разворачивали, — не копия. Это файл, который ни разу
не попросили сделать то единственное, ради чего он существует, и момент, когда
попросят, будет худшим из возможных.

## Команды

```bash
npm run backup           # снять копию (и выгрузить, если хранилище настроено)
npm run backup:list      # что лежит на диске
npm run backup:verify    # снять, развернуть, проверить, удалить временную базу
npm run backup:pull      # вернуть последнюю копию из хранилища
```

Восстановление в конкретную базу:

```bash
node scripts/backup.mjs restore --file backups/anyq-anyq_dev-2026-09-08.sql.gz --into anyq_restored
```

Скриптy не нужен установленный `psql`: клиентские утилиты берутся из Docker.
Версия выбирается под сервер, а не наугад, — `pg_dump` отказывается говорить с
сервером новее себя, и на машине с более старым клиентом получается либо
непонятная ошибка, либо, что хуже, неполный дамп.

Две базы — два случая, и скрипт различает их сам:

| Где база | Откуда клиент |
|---|---|
| Локальная, в контейнере `anyq-db` | из этого же контейнера — версии совпадают по построению |
| Боевая на Railway | одноразовый контейнер `postgres:<версия сервера>`, версию спрашиваем у самого сервера |

**До 2026-09-10 второго случая не было вовсе.** Скрипт всегда брал клиент из
локального контейнера, а он PostgreSQL 16 при боевом сервере 18 — то есть
`npm run backup` против боевой базы падал на `server version mismatch`, и
боевую копию этой командой снять было нельзя. Регламент при этом описывал
процедуру так, будто она работает везде. Хартия делает проверенное
восстановление условием запуска, и условие это не выполнялось ни разу.

Проверено 2026-09-10 на боевой базе целиком: копия снята, развёрнута во
временную базу, сверка остатка с журналом сошлась, временная база удалена.
Версию сервера скрипт определил сам и назвал в первой строке вывода.

## Что именно проверяется

`verify` разворачивает копию во временную базу и задаёт ей три вопроса:

1. **В каждой таблице столько же строк, сколько в источнике.**
2. **Схема на той же миграции.** Копия, поднятая на старой миграции, запустится
   и упадёт на первой же записи — это хуже, чем не подняться вовсе.
3. **Остаток сходится с журналом движений** по товару, точке и ячейке.

Третий пункт — единственный, который на самом деле про этот продукт. Это
инвариант, на котором стоит каждая цифра в ANYQ. Копия, восстановившая все
строки и сломавшая его, прошла бы любую общую проверку и всё равно была бы
бесполезной: магазин поднимется с числами, которые нечем обосновать, а это
неотличимо от потери данных.

Временная база удаляется в любом случае — и после успеха, и после провала, —
чтобы неудачная проверка не оставляла мусор, из-за которого не пройдёт
следующая.

Код возврата: `0` — копия годна, `1` — нет. Годится для cron и CI без разбора
вывода.

Проверка проверялась: из копии дампа вырезали десять строк движений, и
`verify` отчитался и о недостаче строк, и — независимо — о разошедшемся
остатке.

## Расписание на пилоте

| Когда | Что |
|---|---|
| Ежедневно, само | служба `backup` на Railway (см. ниже) |
| Ежедневно после закрытия смены, если службы ещё нет | `npm run backup` |
| Еженедельно | `npm run backup:verify` |
| Перед каждым развёртыванием | `npm run backup` |
| Перед миграцией схемы | `npm run backup` и **дождаться** `verify` |

Хранить не меньше семи ежедневных копий. `node scripts/backup.mjs create --keep 7`
удаляет всё, что старше семи последних.

## Куда класть копии

Каталог `backups/` **не в репозитории** — там реальные данные магазина.

На пилоте копия должна уезжать с той же машины, где стоит база. Диск, который
умрёт, унесёт и базу, и копию, лежащую рядом с ней, и наличие копии в этот
момент будет неотличимо от её отсутствия.

## Если восстанавливать пришлось всерьёз

1. **Остановить API.** Пока он пишет, восстановление гонится с ним.
2. `npm run backup:list` — выбрать последнюю копию, прошедшую проверку.
3. Развернуть **рядом**, не поверх:
   `node scripts/backup.mjs restore --file <копия> --into anyq_recovered`
4. Посмотреть глазами: последние продажи, последняя смена, остатки по паре
   ходовых позиций. Это занимает две минуты и отвечает на вопрос «сколько
   работы потеряно», на который дамп сам по себе не отвечает.
5. Только после этого переключать `DATABASE_URL` на восстановленную базу.

Разворачивать поверх рабочей базы скрипт отказывается без `--force`. Это
намеренно: иногда это и есть правильное действие, но никогда — по случайности
и никогда — как побочный эффект проверки копии.

## Копия вне машины

Дамп, который лежит только на той же машине, что и база, — не резервная копия
этой машины. Диск умирает вместе с ней.

```
node scripts/backup.mjs create --mirror D:/anyq-backups
```

Путь можно задать один раз через `ANYQ_BACKUP_MIRROR`, и тогда `npm run backup`
делает это сам. Куда именно — решает владелец: примонтированная сетевая папка,
второй физический диск, что угодно, что переживёт смерть первого.

Копия не считается сделанной, пока не прочитана обратно: скрипт считает sha256
оригинала, копирует, читает копию и сравнивает. Совпало — пишет хеш в лог. Не
совпало или каталог недоступен — падает с ненулевым кодом и говорит, что
проверить. Это не перестраховка: копия на полку, которая молча обрезала файл,
выглядит ровно как удачная — ровно до того утра, когда она осталась одна.

Старые копии удаляются (`--keep N`) только после того, как новая доказана вне
машины. Неудачная копия никогда не оставляет резервных копий меньше, чем было
час назад.

Проверять её нужно так же, как местную, и по тому же файлу:

```
node scripts/backup.mjs verify --file D:/anyq-backups/anyq-...sql.gz
```

Это разворачивает именно ту копию, что лежит вне машины, и проверяет на ней
сходимость остатка с журналом. Совпадение хешей говорит, что байты те же;
`verify` говорит, что из них поднимается магазин.

## Копия вне комнаты: хранилище

Второй диск спасает от одного отказа — того, что случается с диском. От пожара,
кражи ноутбука и удалённого по ошибке контейнера он не спасает: обе копии в
одной комнате.

```bash
node scripts/backup.mjs create --upload   # снять и выгрузить
node scripts/backup.mjs pull              # вернуть последнюю обратно
node scripts/backup.mjs pull --verify     # …и сразу доказать восстановление
```

Хранилище — любое S3-совместимое: Cloudflare R2, Яндекс, MinIO на своём
сервере, AWS. Ни одна из этих компаний не обязательна, и ни к одной из них
копии не привязаны: протокол один и тот же.

### Что задать

| Переменная | Что это |
|---|---|
| `ANYQ_BACKUP_S3_ENDPOINT` | адрес хранилища, например `https://s3.eu-central-1.amazonaws.com` |
| `ANYQ_BACKUP_S3_BUCKET` | имя бакета |
| `ANYQ_BACKUP_S3_KEY` | идентификатор ключа доступа |
| `ANYQ_BACKUP_S3_SECRET` | сам ключ |
| `ANYQ_BACKUP_S3_REGION` | регион; для R2 и MinIO подходит `auto` |
| `ANYQ_BACKUP_S3_PREFIX` | папка внутри бакета, по умолчанию `anyq/` |
| `ANYQ_BACKUP_S3_KEEP` | сколько копий хранить, по умолчанию 14 |
| `ANYQ_BACKUP_S3_PATH_STYLE` | `no`, если поставщик требует адрес вида `bucket.endpoint` |

Когда эти переменные заданы, `npm run backup` выгружает копию сам — флаг не
нужен. Когда не заданы, а `--upload` передан, команда падает с ненулевым кодом
и говорит, чего не хватает: молчаливое «наверное, не надо» — это ровно тот
способ, которым копии перестают сниматься и никто об этом не узнаёт.

### Чем это проверено

Копия не считается выгруженной, пока не прочитана обратно: скрипт считает
sha256, кладёт объект, скачивает его целиком и сравнивает. Не совпало — падает
и говорит, что копию считать несделанной. Старые копии удаляются только после
того, как новая прочитана обратно, — неудачная ночь никогда не оставляет копий
меньше, чем было вчера.

Проверено на настоящем S3-сервере (MinIO в контейнере), а не на моках: положить,
прочитать побайтово, перечислить, удалить лишние по сроку хранения. Полный круг
— снять дамп, выгрузить, скачать обратно, развернуть во временную базу — прошёл
целиком: 34 таблицы, та же миграция, остаток сходится с журналом.

Повторить проверку у себя:

```bash
docker run -d --name anyq-minio -p 9100:9000   -e MINIO_ROOT_USER=anyqtest -e MINIO_ROOT_PASSWORD=anyqtest12345   quay.io/minio/minio server /data
docker exec anyq-minio mkdir -p /data/anyq-backups && docker restart anyq-minio

ANYQ_BACKUP_S3_ENDPOINT=http://127.0.0.1:9100 ANYQ_BACKUP_S3_BUCKET=anyq-backups ANYQ_BACKUP_S3_REGION=us-east-1 ANYQ_BACKUP_S3_KEY=anyqtest ANYQ_BACKUP_S3_SECRET=anyqtest12345 npm run backup
```

## Копии по расписанию, без участия человека

Копия, которую снимает человек, не снимается в тот день, когда человек забыл.
Отдельная служба на Railway делает это сама.

Один раз:

```bash
railway add --service backup --repo <owner>/<repo> --branch main   --variables "DATABASE_URL=<тот же, что у api>"   --variables "NIXPACKS_PKGS=postgresql_16"   --variables "ANYQ_BACKUP_S3_ENDPOINT=..."   --variables "ANYQ_BACKUP_S3_BUCKET=..."   --variables "ANYQ_BACKUP_S3_KEY=..."   --variables "ANYQ_BACKUP_S3_SECRET=..."
```

Затем в настройках службы задать **Cron Schedule** — например `0 19 * * *`
(полночь по Алматы: Railway считает в UTC). Служба просыпается, снимает копию,
выгружает её и завершается; Railway показывает красное, если она завершилась с
ошибкой, — а копия, которой нет, должна быть заметна.

`NIXPACKS_PKGS=postgresql_16` обязателен: внутри контейнера Docker нет, и
`pg_dump` должен быть в самой сборке. Версия должна совпадать с версией сервера
— скрипт сверяет их сам и отказывается снимать копию несовпадающим клиентом,
потому что старый `pg_dump` отдаёт неполный дамп молча. Если база переедет на
PostgreSQL 17, эту переменную надо поменять; скрипт скажет об этом в первый же
запуск.

Что этот путь проверен: скрипт целиком прогнан в контейнере без Docker внутри,
с `pg_dump` из системы — снял дамп боевого размера, выгрузил, прочитал обратно,
удалил лишнюю по сроку хранения. Ровно то, что будет делать служба.

## Чего здесь нет

Шифрования дампов. И восстановления на точку во времени: для этого нужен
WAL-архив, а он имеет смысл после перехода на управляемую базу.

## Переезд на другой сервер

```bash
node scripts/backup.mjs move --to "postgres://user:pass@host:5432/anyq"
```

Снимает копию, разворачивает её на указанном сервере и проверяет результат тем
же способом, которым проверяется любая копия: построчная сверка по каждой
таблице, та же миграция, остаток сходится с журналом движений. Не сошлось —
ненулевой код выхода и прямая строка «приложение переключать нельзя».

Зачем это нужно, а не «приятно иметь»: **боевая база стоит в Сан-Франциско**
(Railway, регион `sfo`), а в ней имена, телефоны, адреса доставки и ИИН
контрагентов — персональные данные граждан Казахстана, которые
[закон](https://www.adilet.zan.kz/rus/docs/Z1300000094) и
[правила обработки](https://adilet.zan.kz/rus/docs/V2000021498) требуют хранить
на территории РК. Пока база там, коммерческий запуск в Казахстане стоит на
юридическом риске, а не на техническом. Эта команда — тот инструмент, которым
риск закрывается, и она проверена на настоящем переносе, а не описана.

Трафик команда не переключает. Это сделано намеренно: перевести приложение
значит поменять `DATABASE_URL` у четырёх служб и выбрать минуту, когда магазины
останутся без кассы, — решение человека. Всё, что продано между снятием копии и
переключением, останется в старой базе, поэтому порядок такой:

1. Предупредить магазины о перерыве.
2. `move --to <новый адрес>` — перенос и проверка.
3. Поменять `DATABASE_URL` у `api`, `admin`, `pos`, `orders`.
4. Снять копию уже с новой базы и проверить: `node scripts/backup.mjs verify`.

**База уезжает вместе со службами, а не одна.** Если оставить `api` в
Сан-Франциско, а базу поставить в Казахстане, каждый запрос к базе пойдёт через
океан. Один экран кассы — это десятки запросов; при задержке в двести
миллисекунд открытие смены превращается из мгновенного в секундное, а список
товаров — в «подождите». Продукт станет медленнее, чем был, и формально
законным. Переезд ради закона — это переезд всего: пяти служб и базы, в один
регион, желательно в один дата-центр.

Базу на той стороне команда не создаёт: у управляемого хостинга на это обычно
нет прав, зато база там уже есть — её дают вместе с адресом. Непустую не трогает
без `--force`: самая дорогая ошибка здесь — залить дамп поверх работающей базы.

Проверено 2026-09-10 на настоящем переносе: 34 таблицы, 715 строк, миграция
совпала, остаток сошёлся с журналом. Сверка при этом доказана от обратного — на
перенесённой базе удалены движения, и проверка назвала 55 расхождений вместо
того, чтобы промолчать.
